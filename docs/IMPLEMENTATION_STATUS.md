# Implementation Status

## What Is Implemented

The application has a functional multi-tenant production workspace foundation. It provisions a private organization and workspace when a signed-in user opens the application, scopes projects, assets, jobs, Copilot actions, research records, transcripts, and other domain objects to that workspace, and applies owner, admin, editor, reviewer, viewer, and client roles through tenant-aware server checks.

The creator workflow supports project creation, structured AI script generation, source-recorded research, provenance-labelled claim extraction, AI image generation, S3-backed asset upload, asset-rights status, Whisper-based transcription, SRT/VTT export, asynchronous job records, cancellation and retry controls, and an action-only Copilot. The Copilot uses a constrained tool schema and persists the selected tool, JSON parameters, approval state, job reference, and audit event rather than emitting an unstructured conversational answer.

The user interface includes a responsive dark/light production shell, workspace switching, dashboard, Script Studio, Research workspace, Media Library, Scene Editor foundation, Voice & Captions, job operations, agency/client workspace controls, and the action log for executable Copilot commands. Voice & Captions now lets a creator select an approved workspace voice, see whether it has a ready allowed provider, submit narration text, and preview the persisted audio asset after synthesis; the server remains responsible for provider mapping and verified commercial-consent enforcement.

## Deliberate Integration Boundaries

The application does **not** fabricate social connections, publishing success, analytics, render output, commercial model rights, or provider availability. The Publishing workspace now provides a project-linked calendar and agenda, governed platform-copy adaptation, account readiness, review-state visibility, persisted editable variants, approval records, account assignment, idempotent dispatch attempts, and a protected scheduled-dispatch callback. Workspace administrators can disconnect a connected account locally through a confirmation control; this removes its credential reference and invalidates only plans that could still dispatch, while preserving published and cancelled history. Direct production actions still require the corresponding official APIs, secure OAuth credentials, platform approvals, a published callback deployment, and worker deployment.

Production FFmpeg rendering, open-source TTS deployment, local-model inference, GPU video generation, scheduled publication, and social analytics synchronization must run in separate worker infrastructure. They cannot be safely performed as long-running work inside a request-scoped web process. Their interfaces, job types, data model, and user-visible status states are already represented in the product foundation.

| FFmpeg rendering and GPU jobs | Deploy a dedicated CPU/GPU worker environment with private object-storage access and a queue consumer. The high-fidelity manifest requests 30 fps H.264 at 12 Mbps with 48 kHz / 192 kbps AAC; the worker must honor or explicitly reject that contract. |

## Download-first export scope

Cross-platform publishing now has a safe workflow foundation but is not activated until the user elects to publish to a platform and provides that platform’s official credentials. The current product exposes export presets for landscape, vertical, and square output, plus explicit **Standard** and **High fidelity** private-worker profiles. High fidelity is the default production contract: 30 fps H.264 at 12 Mbps with 48 kHz / 192 kbps AAC. The application submits versioned video documents to a private render-worker boundary, records completed worker-returned video files as tenant-scoped video assets, and generates signed download URLs only after access checks. A render worker must return a `storageKey` in its JSON response for an export to become downloadable.

For immediate use without credentials or a worker, the public **Guest Quick Draft** route (`/quick-draft`) creates a browser-local WebM without sign-in, a project, provider calls, uploads, or persistence. Users enter a title and short script, choose landscape, vertical, or square framing plus Preview, Standard, or High local quality, then create an in-browser preview and explicitly download it. The authenticated Scene Editor provides the same quick-draft flow for saved project scenes. The active render can be cancelled; cancellation stops the recorder and canvas-media tracks, and unmount cleanup aborts an in-flight preview to prevent stale UI updates. Both draft routes are intentionally labelled as visual and silent: they render scene cards and text, are capped at 24 seconds, do not synthesize a natural voice or photoreal footage, and never upload video to the server. The worker path remains the production route for final MP4 assets.

## Realistic and long-form production boundary

The local browser renderer is deliberately not presented as a model-tuned, hyper-realistic video system. Natural speech, photoreal generated footage, lip synchronization, music mixing, and exports approaching one hour require a private, asynchronous production worker. That worker must combine approved image/video generation models, a licensed neural TTS provider or self-hosted speech model, FFmpeg-based composition, object storage, resumable job orchestration, and tenant-scoped render callbacks.

For responsible operation, the production worker must retain model identifiers, voice and asset licences, prompt and source provenance, requested render-quality profile, job timing, and the output checksum. The application already provides the provider registry, free-first policy gate, render job boundary, approval states, and signed-download records required to attach that worker later. Public Hugging Face TTS remains an approved model-default route; catalog-level natural delivery controls are deliberately reserved for a consent-verified private Kokoro worker. Model fine-tuning or voice cloning must remain opt-in, rights-checked, and implemented only after the chosen provider and deployment environment are configured.
